# Static discovery on a previously accepted runtime

Schema 1 full-runtime releases retain their existing exact commit, integrity,
15 product checks, five scientific/presentation bindings, 72-hour source check
and publication-profile requirements. A missing profile still fails that route.

Schema 2 is restricted to `static_discovery_overlay`. `deployment_commit` and
`static_tool_commit` identify the current protected-main verifier/generator;
`runtime_code_commit` identifies the original deployed runtime. It has no
ambiguous top-level `code_commit`. The trusted repository acceptance digest must
bind both versions, the original raw acceptance and integrity digests, and the
successful original Pages deployment/run. The deployment CLI reads GitHub's
historical deployment, successful workflow and original `EXPECTED_SHA256` log;
it does not trust a caller's assertion that a runtime was once accepted.

The original acceptance is revalidated at its actual historical publication
time, not re-dated. Its five bindings remain identical. The new receipt still
requires all fifteen checks and a new candidate-bound, current source check.
Source availability evidence is not a claim of updated data or complete crime
coverage. A current provider-listing check may be adopted with its actual
observed timestamp and evidence, retaining that limited scope.

The complete original inventory is embedded in the detached new inventory.
Every original non-discovery asset must retain its exact SHA and byte count;
no runtime/data file may be removed or added. Original HTML bytes must match
that inventory. The verifier regenerates discovery output from those bytes and
the current committed city catalog, requiring byte-identical output. Arbitrary
HTML, changed script references, extra assets and resealed new runtime bundles
fail. CSP, private-content, file/path/count/size and sitemap/language checks still
run on the complete combined artifact.

If the historical artifact already has the complete publication profile, the
ordinary profile verifier still runs. A historical pre-profile runtime is
accepted only through the independently verified unchanged full-inventory
contract, reported explicitly as
`accepted_pre_profile_runtime_inventory_preserved`. No profile is invented or
copied from a newer build. This compatibility route cannot publish a new runtime
or new city dataset, and does not certify the unaccepted 3D/memory candidate.

Release assets remain the three detached files: `site.tar.gz`,
`site-integrity.json`, `site-acceptance.json`. The archive remains immutable and
bounded; the new inventory and acceptance are outside it. Update the trusted
acceptance digest only for the audited new release, then use the existing Pages
workflow. Successful public HTTP checks establish that discovery files are
online; they do not establish actual search-engine indexing.
